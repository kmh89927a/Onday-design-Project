# JTBD A/B 테스트 — 진단 입력 화면 (`/diagnosis`)

> 대상: OnDay 진단 입력 화면 A vs JTBD 기반 Variant B · 집중 Force: **Anxiety(데이터 신뢰성) 완화 1개**
> 근거: JTBD 14명 인터뷰(`my-동네궁합진단기-workbase/raw/assets/10_jtbd-interview-report.md`) · 화면 코드(`onday-app/src/app/diagnosis/page.tsx`) · 측정(`onday-app/src/lib/analytics/mixpanel.ts`, 수요일 #241 배선)
> ⚠️ 가정: A안 기준선 수치 = 표본 빈약(이벤트 배포 수일·저트래픽)으로 **구조·인터뷰 기반 추정** — 실측 아님. 수치는 운영 후 채움.

---

## 1. 테스트 목적

**단일 질문:** 진단 입력 화면에서, A안(주소 입력 요청 중심)보다 **B안(데이터 신뢰성 불안을 먼저 완화)**을 보여줄 때 **입력→제출 전환이 더 일어나는가?**

진단 입력 화면은 OnDay 진단 퍼널의 **최대 입력 부담 지점**(주소 2건 + 필터)이고, JTBD 14명의 지배적 이탈 동인은 **"이 데이터/스코어가 실제와 다를까봐"의 불안**이다. 이 실험은 "더 예쁜 문구"가 아니라 **불안 완화라는 전환 논리**가 입력 행동을 바꾸는지 확인한다.

## 2. 현재 화면 A 진단

| 항목 | 내용 (코드 근거) |
|------|------------------|
| 자극 Force | **Push**(수동 검색·엑셀 취합 번거로움)에 의존 — "두 분의 직장 주소를 알려주세요"(`page.tsx:327`)로 곧장 입력 요청 |
| 핵심 약속 | 두 직장 주소 → 교집합 동네(Pull) |
| 잘 다루는 동기 | Push(번거로움 탈출) + 진입 단순성(STEP 1/2, `page.tsx:322`) |
| 놓치는 불안/장벽 | ★ **데이터 정확성 Anxiety 미완화** — 유일한 신뢰 카피 "입력한 주소는 분석 후 자동 삭제돼요"(`page.tsx:340`)는 **프라이버시** 불안만 다루고, JTBD 지배 불안인 "예측치가 실제 통근과 다를까"·"스코어가 실생활과 안 맞아 잘못된 결정 내릴까"는 화면에서 미해소. 데이터 출처(카카오·ODsay·국토부·행안부)는 랜딩 하단(`landing-client.tsx:523`)엔 있으나 **입력 화면엔 부재** |
| 가장 큰 약점 | 입력 부담(주소 2건+필터)은 높은데 **"이 수고가 정확한 답으로 보상된다"는 신뢰 신호가 입력 직전에 없음** → 망설임·이탈 |

## 3. Variant B 실험 가설

> **만약** 맞벌이 부부/이사 예정자가 진단 입력 화면에서
> **기존 부동산 앱의 부정확·불일치 경험 때문에 "이 진단도 실제와 다를까봐"** 망설이고 있다면,
> 현재 A안보다 **입력 직전에 "실데이터 출처 + 실제 통근 기반"임을 보여주는 신뢰 신호**를 제시할 때
> **진단 제출(diagnosis_submit_clicked)**이 더 많이 발생할 것이다.
> **왜냐하면** B안은 고객의 **Anxiety(데이터 신뢰성)**를 입력 부담을 감수하기 전에 완화하기 때문이다.

| 항목 | 내용 |
|------|------|
| 핵심 가설 | 데이터 신뢰 불안 완화 → 입력 부담 감수 의향↑ → 제출률↑ |
| 자극/완화 Force | **완화: Anxiety(데이터 정확성·실제 일치)** — 단일 Force |
| 기존 대안 | 직접 검색 + 엑셀 수동 취합, 중개사 말(신뢰 불가), 부동산 앱(단일 직장 기준) |
| 전환 장벽 | "수고 들여 입력해도 결과가 부정확/실생활 불일치일까" |
| 강조 메시지 | 카카오 모빌리티·ODsay·국토부 실거래가·행안부 안전지수 = **실데이터 기반**, "실제 통근 시간으로 계산" |
| 기대 행동 변화 | 입력 화면 진입자 중 제출 클릭 비율 상승 (1차 지표) |

## 5. Variant B 화면 시나리오

| 구성 | B안 내용 |
|------|---------|
| 헤드라인 | 두 직장의 **실제 통근**으로 동네를 찾아드려요 |
| 서브카피 | 카카오 모빌리티·ODsay·국토부·행안부 실데이터 기반 · 입력 주소는 분석 후 자동 삭제 |
| CTA | 진단 시작 (동일) |
| 보조 설명 | "예측이 아니라 실제 도로·대중교통 경로로 계산합니다" |
| 신뢰 요소 | 데이터 출처 배지 4종(자차/대중교통/시세/안전) — 입력 폼 상단 노출 |
| 불안 해소 문구 | "실거주 후 통근이 달라질까 걱정되시죠 — 실시간 경로 데이터로 오차를 줄였어요" |
| 습관 전환 장치 | "엑셀로 일일이 취합하던 걸, 두 주소만 넣으면 끝" *(A안에도 존재하는 기존 저입력 요소 — B의 변경 레버 아님. B의 단일 변경 레버 = Anxiety 완화)* |

**사용자 흐름 6단계:** ① 입력 화면 진입(노출) → ② 데이터 출처 배지·신뢰 카피 인지 → ③ 내 직장 주소 입력 → ④ 배우자 직장 주소 입력(주소 2건 검증) → ⑤ "진단 시작" 클릭(제출) → ⑥ 결과 화면(진단 완료).

## 6. 최소 측정 계획 (★ 수요일 기존 이벤트만 — 새 이벤트 0)

> 매핑되는 이벤트는 전부 #241(수요일) 배선분. **신규 이벤트 추가 없음.**

| 측정 항목 | 기존 이벤트 | 위계 |
|-----------|-------------|------|
| 화면 노출 | `diagnosis_input_viewed` (분모) | — |
| CTA 클릭(제출 시도) | `diagnosis_submit_clicked` | **1차 주 지표** |
| 주소 입력 진척 | `address_verified`(count 1/2) | 보조(진척) |
| 목표 행동 완료 | `diagnosis_completed` | **2차 보조** |
| 중도 이탈 | `input_viewed` 발생 & `submit_clicked` 없음 | — |

**계산식 (위계 반영):**

```text
[1차 주 지표] 입력 화면 전환율 = diagnosis_submit_clicked / diagnosis_input_viewed
   → 입력 화면 "순수 전환 효과". A/B 차이를 이 지표로 1차 판정.
[보조-진척]  주소 완료율   = address_verified(2건) / diagnosis_input_viewed
[2차 보조]  진단 완료율   = diagnosis_completed / diagnosis_input_viewed
   → 북극성 연결. 단 제출 後 API 성공·결과 렌더 등 후속 단계 변수가 섞임(입력 화면 단독 효과 아님).
[참고]      클릭후 완료율 = diagnosis_completed / diagnosis_submit_clicked
```

⚠️ **A안 기준선:** 현재 표본 빈약(이벤트 배포 수일·저트래픽) → 가정 기준선으로 시작하고, 충분 표본 전엔 "확정" 아닌 **학습 신호**로 해석. 수치 미창작.

## 7. 결과 해석 기준 (★ 1차 지표 중심, 완료율은 보조)

| 결과 (1차=전환율, 2차=완료율) | 해석 | 다음 행동 |
|------|------|-----------|
| B 1차↑ & 2차↑ | 불안 완화가 입력 화면 전환을 키웠고 완료까지 이어짐 | **B를 기본안 반영** |
| B 1차↑ & 2차↓ | 제출은 늘었으나 후속(API·결과 신뢰) 이탈 — 입력 화면 효과는 유효 | B 채택 + 결과 화면 신뢰·로딩 UX 별도 점검 (입력 화면 성공으로 읽음) |
| B 1차↓ & 2차↑ | 유입 제출은 줄었으나 진성 사용자 품질↑ | 타겟 문구 구체화, 표본 더 확보 |
| A가 1차에서 더 좋음 | 이 고객엔 Push(번거로움 탈출)가 더 직관적 | A 유지, B의 출처 배지만 일부 병합 |
| 1차 차이 거의 없음 | 메시지보다 유입·기능·표본 문제일 수 있음 | 인터뷰 재확인 또는 입력 부담(구조) 테스트로 전환 |

> ★ **판정 우선순위:** 1차(`submit_clicked/input_viewed`)로 입력 화면 순수 효과를 먼저 읽고, `diagnosis_completed`(2차)는 **후속 단계 변수가 섞임을 인지**한 채 방향 확인용으로만 본다.

## 8. 주의사항 (A/B 불변식 + 과대해석 금지)

- **같은 고객** — A·B 모두 진단 입력 화면 도달자(맞벌이 부부/이사 예정자) 동일 노출. 세그먼트 분리 금지.
- **같은 화면·같은 CTA 목적** — 둘 다 `/diagnosis`에서 "진단 시작(제출)" 동일. CTA 문구·목적 불변.
- **하나의 Job Story** — "두 동선 교집합 동네를 정확히 찾고 싶다" 1개만.
- **핵심 전환 논리 1개만 변경** — Anxiety(데이터 신뢰) 완화 **1 Force만**. 입력 항목·필터·기능은 A와 동일(기능 테스트화 금지).
- **변경 레버 명확화** — 변경하는 단일 Force = **Anxiety 완화(출처 배지)**. 화면에 존재하는 Habit·Pull 요소는 A·B 공통으로 유지되며 변경 대상 아님.
- **기준선 필요** — 현재 표본 빈약이므로 ⚠️ 가정 기준선. 충분 표본·기간 전엔 **학습 신호**로만 해석, "확정" 금지.
- **과대해석 금지** — `diagnosis_completed`(2차)는 제출 後 변수가 섞이므로 입력 화면 단독 효과로 읽지 않는다. 1차 지표가 판정 기준.

> ⚠️ 가정 목록: A안 기준선 수치(표본 빈약) · B안 카피는 제안안(실제 디자인 확정 전) · 데이터 출처 배지의 입력 화면 노출은 신규 UI(미구현, 본 실험 채택 시 구현 대상).
